# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Java library for sending and receiving protobuf messages over TCP with no netty/mina dependency.

**Status: 2.0, feature-complete, not yet released to Maven Central** (version `2.0.0-SNAPSHOT`). 2.0 is a rewrite on virtual threads with blocking sockets, a new API (`ProtoClient` / `ProtoServer` / `ProtoConnection`), TLS, backpressure and a one-time protocol preamble. The frame format is unchanged. There's no backward compatibility with 1.x, which had no users. 1.x (async NIO, `java.nio.channels.Asynchronous*`, no TLS) is gone from `master`; its last version is the git tag `1.x-final`, the reference for 1.x behaviour, its tests (`ChannelRobustnessTest`) and its benchmark baseline. The README documents the 2.0 API for users and must stay in step with it (configuration table, defaults, threading contract).

## Build & test

Maven multi-module project compiled for Java 25 (`maven.compiler.release=25`). Java 25 is the baseline because 2.0 moves to virtual threads, which pin carrier threads inside `synchronized` before JDK 24 (JEP 491). Building requires JDK 25+ (enforcer) and Maven 3.9+. Always build with the Maven Wrapper (`./mvnw`, pinned to Apache Maven 3.9.12): Ubuntu's packaged `/usr/bin/mvn` can't load the ascopes protobuf plugin (it fails with a Guice `NullInjectedIntoNonNullable` error). On this machine JDK 25 is at `/usr/lib/jvm/java-25-openjdk-amd64`, but the default `java` is 21, so set `JAVA_HOME` if needed.

```bash
./mvnw clean install                       # build all modules
./mvnw test -pl protobuf-nio-core          # core unit tests only
./mvnw test -pl protobuf-nio-core -Dtest=ProtobufSerializerTest            # single test class
./mvnw test -pl protobuf-nio-core -Dtest=ProtobufSerializerTest#testName   # single method
```

All dependency and plugin versions live as properties in the root `pom.xml` (`dependencyManagement` with the JUnit and Log4j BOMs, plus `pluginManagement`). Modules declare dependencies without versions. Tests use JUnit Jupiter (JUnit 6), run by surefire 3.x. CI is GitHub Actions (`.github/workflows/build.yml`): it builds, tests and checks the Javadoc with Temurin 25 by running `./mvnw -B verify javadoc:javadoc`.

**Changelog:** `CHANGELOG.md` (Keep a Changelog). Add every user-visible change under `## [Unreleased]`; a release renames that section to the version and date. Don't mention 1.x in it or in other user-facing docs. The README's "Versioning" section defines what the semantic versioning covers (the API package, the wire protocol, the minimum Java version).

**Releasing:** pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml` (CONTRIBUTING.md has the steps): it checks the tag against the POM version and that `CHANGELOG.md` has a `## [X.Y.Z]` section, runs `-P release clean deploy -Dgpg.signer=bc` with the secrets `CENTRAL_TOKEN_USERNAME`, `CENTRAL_TOKEN_PASSWORD`, `MAVEN_GPG_KEY`, `MAVEN_GPG_PASSPHRASE`, then creates the GitHub release from that changelog section. "Run workflow" is a dry run (version without `-SNAPSHOT`, `skipUpload`, bundle kept as an artifact). The `release` profile in the root POM (`./mvnw -P release deploy`) attaches sources and Javadoc jars, signs every artifact with `maven-gpg-plugin` (`bestPractices`: the passphrase only from `MAVEN_GPG_PASSPHRASE` or the agent; `-Dgpg.signer=bc` takes the key from `MAVEN_GPG_KEY`, for CI), and uploads a bundle with `central-publishing-maven-plugin` (server id `central` in `settings.xml`, holding a Portal user token). By default the deployment waits on the Central Portal for a manual "Publish" (`-Dcentral.autoPublish=true` skips that). `-Dcentral.skipUpload=true` stops after building `target/central-publishing/central-bundle.zip`, which is how to check what would be published (only the parent POM and core; the sample sets `skipPublishing`, `gpg.skip`, `maven.source.skip` and `maven.javadoc.skip`). Central rejects `-SNAPSHOT` versions for releases.

**`llms.txt`** (repo root) is the summary for coding agents that use the library: install, one complete example, the API at a glance, the rules most often got wrong, links into the README. Keep it in step with the API and the README; its Java block is compiled by `ReadmeExamplesTest` (a block starting with `import` is compiled as a complete file). A release updates its version.

**Javadoc is enforced:** `maven-javadoc-plugin` runs with `doclint=all` and `failOnWarnings`, so every public element of the API package needs a comment, plus `@param`, `@return` and `@throws` (builder settings included: `@return this builder`). Check with `./mvnw -pl protobuf-nio-core javadoc:javadoc`. The `internal` package isn't documented (not exported), and the sample module skips Javadoc (`maven.javadoc.skip`). The package overview is in `package-info.java`.

Protobuf code is generated at build time by `io.github.ascopes:protobuf-maven-plugin`, with the `protoc` version tied to `${protobuf.version}`:
- core: `src/test/proto/TestHeartBeat.proto` → test classes (`generate-test`)
- sample: `src/main/proto/HeartBeat.proto` → main classes (`generate`)

`protobuf-nio-sample` is built but not meant to be published. Its "tests" (`SampleServer`, `SampleClient`, `SampleClientBenchmarkTest`, `MultiClientsTest`) are `main()` programs in `src/main`, not JUnit tests, so the build only compiles them. Run them after `./mvnw install`: start the server with `./mvnw -q -pl protobuf-nio-sample exec:java -Dexec.mainClass=io.github.quantranuk.protobuf.nio.sample.SampleServer`, then run a client the same way in another terminal. `MultiClientsTest` opens 15,000 connections, so both processes need `ulimit -n` above that.

## Architecture (protobuf-nio-core)

**Public API** (`io.github.quantranuk.protobuf.nio`), following the approved 2.0 API:
- `ProtoClient`: a single-use client, built by a reusable `ProtoClient.Builder`, with states new, connecting, open and closed. `connect()` throws `IOException`, and no callback is called when it fails.
- `ProtoServer`: binds and accepts connections; each accepted connection is a `ProtoConnection`.
- Callbacks are set on the builders (A2; there are no listener interfaces): `onConnected(Consumer)`, `onMessage(Type.class, MessageHandler)`, `onOtherMessage`, `onRawMessage(Type.class, RawMessageHandler)`, `onSendFailure`, `onDisconnected`. The handler interfaces are nested in `ProtoServer` (taking a `ProtoConnection`) and `ProtoClient` (taking the client). The builders collect them into an immutable `internal.Callbacks<E>` (one per server or client, so builders stay reusable), which dispatches messages by exact class through `internal.TypeDispatcher` (`ClassValue`; unhandled types are logged once per type). The threading contract lives in the `ProtoServer` and `ProtoClient` class Javadoc.
- Shared types: `DisconnectReason`, `SendException`, `OverflowPolicy`, `TlsClientAuth`.

The public builders delegate validation to `internal.ConnectionConfig.Builder`. Everything in the approved API is implemented.

`module-info.java` (module `io.github.quantranuk.protobuf.nio`) exports only the API package and `requires transitive com.google.protobuf` (an automatic module; the lint warning is suppressed) and `requires org.slf4j`. On the module path, consumers must export the packages of their generated classes to this module, because `MessageTypes.parserOf` calls `getDefaultInstance()` reflectively; the resulting `IllegalAccessException` names the `exports ... to ...` line to add. Tests are compiled into the module and run on the module path (surefire's default patching); the core pom adds `--add-modules jdk.management --add-reads io.github.quantranuk.protobuf.nio=java.management,jdk.management` for test compile and surefire, for `AllocationTest`.

Implementations live in the non-exported `io.github.quantranuk.protobuf.nio.internal` package:
- **`DefaultProtoClient`**: creates the unconnected `Socket` and its `Connection` when `connect()` starts, so sends made while connecting are queued by the connection. Then it connects with `connectTimeout`, calls `start()` and waits on `handshake()`. On failure it calls `Connection.abort()`, which fails the handshake, drops the queue silently and completes `closedFuture`. `close()` while connecting closes the socket, so `connect()` throws.
- **`DefaultProtoServer`**: a blocking accept loop on its own virtual thread. At `maxConnections` (which counts every connection in `all`), a new connection replaces the oldest one still in its handshake (`Connection.abortHandshake()`, which only closes a connection whose state is still `HANDSHAKING`, so an open one is never evicted and no callback hears of it); without one, it's closed at once. The limit-reached and accept-failure warnings are rate-limited (one per 10 s each, with a count of those not logged). Every accepted socket becomes a `DefaultProtoConnection`, kept in `all` until its `closedFuture` completes and in `open` (which backs `connections()` and `broadcast`) from `onConnected` to `onDisconnected`. `broadcast` encodes once into an `EncodedFrame`, which the writer copies. `close()` closes the listening socket, joins the acceptor, closes every connection in parallel on virtual threads (through `Connection.closeAfterHandshake()`), and waits for each `onDisconnected`. A connection still in its handshake isn't cut off: a client counts as open once it has read the server's preamble, the server only once its reader has read the client's, so the client may already be sending. `closeAfterHandshake()` sets `closeRequested` and arms the close deadline; the reader starts the graceful close (`beginGracefulClose()`, a CAS from `OPEN` to `CLOSING`, without waiting) right after `onConnected`, and the watchdog closes it at the deadline if the handshake never finishes. Cutting such connections off lost everything the client had sent (the CI flake in `serverCloseWhileClientsAreSendingLosesNothing`; `serverCloseDuringTheServerSideHandshakeLosesNothing` reproduces it deterministically with a thread factory that delays one reader). `Connection.close()` itself still closes a handshaking connection at once (the client's `close()` while connecting relies on that). When called from a connection's own thread, it closes that connection in place and doesn't wait for it, to avoid deadlock.

The connection core:

- **`Connection`**: one connection over a connected blocking `java.net.Socket` (blocking streams rather than `SocketChannel`, so TLS can later be a drop-in `SSLSocket`). It has a **reader virtual thread** and a **writer virtual thread**, and reports to an internal `ConnectionListener`: `onConnected`, `onMessage` and `onDisconnected` on the reader thread, `onSendFailure` on the writer thread (except `REJECTED` and `DROPPED`, reported on the sending thread). Listener exceptions are logged and ignored. Reader-only and writer-only fields aren't synchronized; only the send queue (a `ConcurrentLinkedQueue` of messages or pre-encoded `EncodedFrame`s), the counters, the state and the termination are shared.
  - TLS (when `ConnectionConfig.sslContext` is set): `start()` layers an `SSLSocket` over the TCP socket (`stream`; client mode when the constructor got a `tlsHost`, with hostname verification through `setEndpointIdentificationAlgorithm("HTTPS")`; server mode with the client-auth setting). The **reader** runs `startHandshake()` under the handshake timeout, while the writer waits on `tlsReady` before sending the preamble (otherwise the writer's first write would run the handshake without a timeout). `SSLException` maps to `TLS_ERROR`, as does a timeout during the TLS handshake. `terminate()` always closes the TCP socket, never the `SSLSocket` (that would try to send `close_notify` and could block behind a stuck writer). `SSLSocket.shutdownOutput()` works (it sends `close_notify`), so graceful close is the same as without TLS, for TLS 1.2 and 1.3.
  - Handshake: the writer sends the 8-byte preamble (`Protocol`) first. The reader checks the peer's preamble within the handshake timeout (a wrong magic or no common version gives `PROTOCOL_MISMATCH`). `handshake()` completes before `onConnected`. **If the handshake fails, no listener method is called at all.**
  - Reader: one byte array with start and end indices. It starts at 64 bytes, jumps to 8 KB and doubles only while reads fill it (up to `readBufferSize`), and goes back to 64 bytes after `idleShrinkDelay` (1 s) of idleness. A frame bigger than the buffer never gets a buffer of its declared size at once: the buffer grows only when received bytes fill it, to at most twice those bytes (otherwise a 12-byte header announcing 64 MB, then a stall, would cost 64 MB; `announcingAHugeFrameThenStallingCostsLittleMemory` guards it). The class name is resolved as soon as header and name have arrived, before the payload is read, so unknown or disallowed types are rejected without buffering their payload. Peer-supplied class names in exception messages go through `Protocol.quotableName` (non-printable bytes escaped as `\xNN`, cut at 256 characters). `SO_TIMEOUT` is set to the next deadline (handshake, read timeout or idle shrink). Frames are validated (signature, name length 1–4096, payload 0–`maxMessageSize`), and heartbeats (both lengths 0) are skipped. A raw-handler frame isn't parsed: `onRawMessage` gets one reused heap `ByteBuffer` view over the read buffer (dropped whenever the buffer is replaced, so it never keeps a big buffer alive). An 8-entry per-reader cache resolves class names to a target: a raw handler (`ConnectionConfig.rawHandlers`, checked first, so raw types are always allowed) or a parser. Behind it sits `MessageTypes`, or, when `allowedMessageTypes` is set, in front of the allowlist (`ConnectionConfig.allowedTypes`, class-name bytes → parser, built from the `Class` objects when the builder is called), so a disallowed name never reaches a class loader and fails with a `ProtocolException` (`PROTOCOL_ERROR`).
  - Writer: drains the queue in batches, **one socket write per batch**. Senders `unpark` it only when it's parked (`writerParked` flag; Dekker-style ordering with the queue). It encodes through one `CodedOutputStream` over the write buffer that serves many batches: each batch is appended after the previous one, and the encoder restarts at offset 0 only when the buffer is full (`ProtobufSerializer.writeFrame`; the header ints go through `writeFixed32NoTag(Integer.reverseBytes(...))`). An encode failure fails that message alone (`WRITE_FAILED`) and restarts the encoder at its offset. It only ever `poll`s the queue (never `peek` then `poll`, because `DROP_OLDEST` senders poll too); a message that doesn't fit the batch is kept in `carry` for the next one. Each message counts as in flight before it's encoded, so a throw can't leak its reservation. It sends a heartbeat when idle for `heartbeatInterval` and releases its batch buffer after `idleShrinkDelay`.
  - Backpressure: `send` reserves room first (CAS loops on `pendingMessages` and `pendingBytes` against `maxPendingMessages` / `maxPendingBytes`; a message larger than `maxPendingBytes` fits only when nothing else is pending), then checks the state, then queues. When the queue is full, `onQueueFull` applies the `OverflowPolicy`. `BLOCK` waits on `roomLock` for up to `sendTimeout`; the writer wakes waiters after each batch and closing wakes them too. It never waits in `send(EncodedFrame)` (broadcast) or on the writer thread. `DROP_OLDEST` polls the oldest message and always reports it as `DROPPED`. `DISCONNECT` rejects, then `terminate(SEND_QUEUE_OVERFLOW)`. `REJECTED` is reported on the sending thread, only while `OPEN` (not during the handshake or closing). Senders in that slow path are counted in `overflowing`, and report inside a `ScopedValue` so that `isListenerThread()` is true for them (server `close()` won't wait for the connection from there).
  - Closing: failures (EOF, bad frame, timeouts, I/O errors) close the socket at once through `terminate()`; the first reason wins. `close()` is graceful: stop accepting sends → writer flushes → `shutdownOutput()` (FIN) → the reader waits for the peer's FIN → close the socket. A plain close with unread input would send a TCP reset and could make the peer lose data. All of this happens within `closeTimeout`, after which the socket is closed regardless. The reader's `finish()` then waits for the writer, fails leftovers with the shared `CLOSED` `SendException`, and calls `onDisconnected` last, exactly once. Before that, `failQueuedAfterClose()` keeps failing the queue until `pendingMessages` and `overflowing` reach zero, so a send that reserved room just before closing can't strand its message, and every sender's report comes before `onDisconnected`.
  - Failures use built-in exceptions, never custom ones: `java.net.ProtocolException` for a bad preamble or frame (also thrown by `connect()`), and `java.net.SocketTimeoutException` for the library's own timeouts (preamble, read, write). The reader derives the `DisconnectReason` from the exception type and whether the handshake has finished: `PROTOCOL_MISMATCH` before it, `PROTOCOL_ERROR` or `READ_TIMEOUT` after.
- **`Watchdog`**: one shared platform daemon thread that enforces the write timeout (blocking socket writes have no timeout in the JDK) and the close deadline, by scanning registered connections at a tenth of the shortest timeout (10 ms to 1 s).
- **`ConnectionConfig`**: immutable settings plus a validating builder (V2's public builders delegate to it). The defaults match the 2.0 API appendix; `TCP_NODELAY` is on by default.
- **`ProtobufSerializer`** (frame encoding): each frame is a 12-byte header of three ints, `SIGNATURE (0x7A6B5C4D)`, class-name length and payload length, followed by the ISO-8859-1 fully-qualified Java class name and the protobuf bytes. `writeFrame` encodes straight into the batch buffer through the writer's reused encoder; `serialize`/`serializeInto` (one allocation per call) serve `EncodedFrame` and tests. Class names are encoded once per class (`ClassValue`).
- **`MessageTypes`**: resolves received class names to parsers through one class loader (`Class.forName(name, false, loader)`, so a class isn't initialised until it's known to be a `MessageLite`), shared per loader through a weak map. Parsers are cached by a private copy of the name bytes, never the caller's buffer.
- Test suites beyond the unit tests: `SoakTest` (8 clients, about 3 s, sessions closed at random from both sides, mixed message sizes; checks every accepted message is received or reported and `onDisconnected` is last and exactly once; prints its seed, `-Dsoak.seed=` replays the random choices) and `ModulePathTest` (compiles a consumer module with `javac` and runs it in a child JVM on the module path against the real, unpatched library module, with and without exporting its generated package).
- `ReadmeExamplesTest` compiles every ```java block of `README.md` (and `llms.txt` when it exists) with `javac` against the real library: each block becomes a method body in a class that declares what examples take for granted (`log`, `update`, `serverContext`, `clientContext`, `running`, `onPriceUpdate`), with the messages from `src/test/proto/ReadmeExamples.proto` (`Ping`, `Pong`, `PriceUpdate`, `LoginRequest`, `OrderRequest`) and `TestHeartBeat`. Blocks starting with `module` are skipped; a fragment without a final `;` gets one. A new example that needs another name means adding it there. A failure names the document and line.
- TLS tests (`TlsTest`) generate self-signed certificates at test time with the JDK's `keytool` (`TestTls`), so no keystore is committed and none expires.
- Both peers need the same generated protobuf classes on their classpath, and renaming or moving a proto class's Java package breaks wire compatibility.

Measured on loopback (JDK 25): about 6–8 KB of heap per idle connection (the figure varies with GC timing; `idleConnectionsStaySmall` prints it), mostly the two parked virtual-thread stacks. `AllocationTest` (platform threads, `ThreadMXBean`) guards the hot path: per message, 24 B on the sender (the `ConcurrentLinkedQueue` node), about 0 on the writer, and on the reader only protobuf's parsing (about 40 B for a small numeric message, 0 with a raw handler). Protobuf itself allocates for string fields on both sides.

`protobuf-java` (4.x) and `slf4j-api` are compile-scope dependencies of core, so consumers get them transitively. Log4j is test scope only in core, so don't add a logging backend to core's compile or runtime scope. Use `MessageLite` rather than `Message` in new API code. On hot paths, block once per batch rather than once per message, and avoid per-message allocation in library code.
